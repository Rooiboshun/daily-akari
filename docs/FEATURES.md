# 機能台帳

このリポジトリに実装されている機能を1枚で見るための台帳。
機能を足した・挙動を変えた・機能を消したときは、同じコミットでここを更新する。

最終更新: 2026-09-21

---

## 状態

盤面ロジック + 遊べる UI + puzz.link との相互変換 + オフライン対応（PWA）。
HTML/CSS/JS だけで動き、ビルドも依存パッケージも無い（`index.html` を
GitHub Pages に置けばそのまま公開できる）。外部への通信は一切しない。
**一度開けば、その後は回線が無くても遊べる**（問題は端末の中で作られるため）。

## 盤面ロジック (`src/akari.js`)

依存ライブラリなしの ES モジュール。ブラウザからも Node からもそのまま読める。

### 盤面の表現

| 機能 | 関数 | 説明 |
| --- | --- | --- |
| テキストから読む | `parse(text)` | `.` 白 / `#` 数字なしの黒 / `0`-`4` 数字つきの黒 |
| テキストに書く | `render(puzzle, state?)` | `state` を渡すと照明を `L` で描く |
| 索引の事前計算 | `buildIndex(puzzle)` | 白マス一覧・各マスから見える範囲・数字マスと隣接白マスを先に作る。黒マスの配置にだけ依存するので、数字を削りながら何度も解く場面で使い回せる |

### ソルバ

| 機能 | 関数 | 説明 |
| --- | --- | --- |
| 制約伝播 | `propagate(ix, st)` | 分岐せずに決まるところだけ埋める。矛盾を見つけたら `false`。三つの規則（照らし合い禁止 / 数字一致 / 全白マス照明）を変化が止まるまで回す |
| 解の数え上げ | `solve(ix, limit)` | 制約伝播＋バックトラック。解を `limit` 個まで返す。一意性の検査は `limit=2` で `count===1` を見る |
| 妥当性の検査 | `isValidSolution(ix, st)` | 完成した配置がルールを満たすか |
| 論理だけで解けるか | `solvableByLogicAlone(ix)` | 分岐なし（制約伝播だけ）で解けるかを調べる。難易度の目安 |

`solve` の戻り値には `guesses`（分岐した回数）、`logicOnly`（一度も分岐せずに
解けたか）、`nodes`（見た節の数）、`aborted`（打ち切ったか）が入る。

`solve(ix, limit, { nodeLimit })` で探索の上限を指定できる（既定は無制限）。
自分で作った問題は数ミリ秒で解けるので上限は要らないが、**外から読み込んだ問題**
（puzz.link の URL）は解が無いまま探索が膨らむことがあるので、画面が固まらない
よう UI 側は上限付きで呼んでいる。上限に達したら `aborted: true` で戻る。

### 盤面生成

| 機能 | 関数 | 説明 |
| --- | --- | --- |
| 一意解の問題を作る | `generate(opt)` | 削り出し方式。①黒マスを 180 度回転対称に配置 → ②全白マスを照らす配置をランダムに作る → ③全黒マスに数字を入れる → ④数字を1つずつ外し、ソルバで一意のままか検査 |
| 打ち切り回数の既定 | `DEFAULT_ATTEMPTS` | 2000。`generate` の既定値であり、`soak` が余裕を測るときの基準 |
| 乱数の種 | `seedFrom(str)` | 文字列から 32bit の種（FNV-1a） |
| 疑似乱数 | `makeRng(seed)` | mulberry32。同じ種なら必ず同じ列 |

`generate` のオプション: `w` `h` `blackRatio` `rng` `logicOnly` `attempts`。
`logicOnly: true` を指定すると「分岐なしで解ける」問題だけを作る。

`attempts`（諦めるまでの試行回数）の既定は **2000**（`DEFAULT_ATTEMPTS` として
公開。道具側が同じ数値を持たずに参照できるようにするため）。盤面の採用率は
実測で easy 10.3% / normal 3.3% / hard 2.4% しかない。捨てられる理由はほぼ全部
「全黒マスに数字を入れてもなお解が一意にならない」で、1回の試行は 0.2〜0.3ms 程度。
打ち切り回数を増やしても、成功する種から出来る問題は変わらない。

既定が 200 だった頃は、種が日付で決まる `dailyPuzzle` で「特定の日だけ、誰が
何度開いても必ず問題が出ない」という形で失敗が固定されていた（2027-01-01 と
2027-06-21）。これは確率的な事故ではなく、当たるまでに 200 回を超える日が
素で存在したということで、**その2日はどちらも `hard` だけが 207 回・237 回**
必要だった（`easy` / `normal` は 3〜74 回で当たっていた）。

余裕は模型ではなく実測で押さえてある。730 日ぶん 2190 問で、当たるまでに要した
回数は easy 最悪 58 回 / normal 最悪 167 回 / hard 最悪 241 回。打ち切り 2000 回は
実測の最悪値に対して **約 8 倍**の余裕がある（幾何分布で見た hard の失敗見込みは
1e-21 程度）。この余裕は `npm run soak` が毎回報告する。

数字の削り出しは1周で済む。数字を外すと解は増えこそすれ減らないので、
一度外せなかった数字は後からも外せないため。結果は
「どの数字を1つ外しても一意でなくなる」極小の問題になる。

### 日替わり

| 機能 | 関数 | 説明 |
| --- | --- | --- |
| 難易度の設定 | `DIFFICULTIES` | `easy` 7x7 / `normal` 9x9 / `hard` 10x10。`hard` だけ試行錯誤を許す |
| その日の問題 | `dailyPuzzle(dateStr, difficulty)` | 日付を乱数の種にするので生成が決定的。サーバも DB も要らず、GitHub Pages のままで「毎日同じ問題が全員に出る」が成立する |
| 今日の日付 | `todayString(date?)` | ローカル時刻を `YYYY-MM-DD` で返す |

## puzz.link との相互変換 (`src/puzzlink.js`)

1日1問では足りないときの供給源として、[puzz.link](https://puzz.link/) の美術館
（pid `lightup`）と問題をやり取りする。依存なしの ES モジュール1枚で、
**外部への通信はしない**（URL 文字列を組み立て／読み解くだけ）。

| 機能 | 関数 | 説明 |
| --- | --- | --- |
| 盤面 → 本文 | `encodeBody(puzzle)` | pzprjs の 4セル符号化 |
| 本文 → 盤面 | `decodeBody(body, w, h)` | 同上の逆。読めない文字・大きすぎる盤面は例外 |
| 盤面 → URL | `toUrl(puzzle, base?)` | `https://puzz.link/p?lightup/<横>/<縦>/<本文>` |
| URL → 盤面 | `fromUrl(text)` | 下記のどの形でも受け取る |

受け取れる形: `https://puzz.link/p?lightup/10/10/…` / `https://pzpr.jp/p.html?lightup/…`
/ 本体だけの `lightup/10/10/…` / このアプリの `#p/lightup/10/10/…`。
`v:` の変種指定とフラグ欄は読み飛ばす。

### 本文の符号（1文字ぶん）

| 文字 | 意味 |
| --- | --- |
| `0`-`4` | 数字つき黒マス |
| `5`-`9` | 数字つき黒マス（値-5）＋後ろに白マス1つ |
| `a`-`e` | 数字つき黒マス（値-10）＋後ろに白マス2つ |
| `.` | 数字なしの黒マス |
| `g`-`z` | 白マスが 1〜20 個続く（36進で読んで -15） |

大きさは **横・縦の順**（`lightup/5/3/` は 5 列 3 行）。取り違えると正方形以外の
問題だけが静かに壊れるので、検証で明示的に固定してある。

出どころは pzprjs（puzz.link が動かしている実装）の `decode4Cell` / `encode4Cell`
と `parseURLData` を読んで規則だけ写したもので、向こうのコードは持ち込んでいない。

規則が本当に上流と同じかは、**上流が自分で書いた問題**と突き合わせて確かめてある
（検証 F6）。pzprjs の `test/script/lightup.js` にある問題 `lightup/6/6/nekcakbl` を
URL と正解の盤面ごと引き写し、(a) 同じ URL から同じ数字配置が出ること、
(b) 書き戻した本文が `nekcakbl` と1文字も違わないこと、(c) こちらのソルバが出す解が
上流の正解と同じ位置に照明を置くこと、の3つを見ている。引き写したのは URL と
盤面の2つの定数だけで、向こうのコードは持ち込んでいない。

> 残っている目視確認: 本物の puzz.link のサイトへ実際に貼って絵として同じ盤面が
> 出るか。符号化の規則は上の F6 で上流の問題と一致することまで裏づけたので、
> これは描画の確認だけが目的の念のための手順。`npm run peek` が最後の行に
> URL を出すので、それを開いて盤面を見比べれば済む。

## プレイ UI (`index.html` / `src/ui.js` / `src/style.css`)

盤面のルールは `akari.js` が全部持っていて、`ui.js` は「描く・触る・数える・
覚えておく」だけを担当する。フレームワークもビルドも使っていない。

| 「置かない」印 | 右クリック / 長押し / `x` キー | スマホ用に「タップ: 照明⇄×印」ボタンでも切り替えられる |
| マスの移動 | 矢印キー | 黒マスは飛び越える |

### 日付とアーカイブ

### puzz.link と行き来する（画面下の折りたたみ欄）

| 機能 | 説明 |
| --- | --- |
| 読み込む | puzz.link の美術館 URL を貼って `この URL を解く`。Enter でも同じ |
| 書き出す | `今の問題を puzz.link で開く`（別タブ）と `URL をコピー` |
| URL | 読み込んだ問題は `#p/lightup/10/10/…`。この形もそのまま貼って開ける |
| 日替わりへ戻る | `今日` か難易度のボタン。最後に遊んだ難易度に戻る |

読み込んだ問題は**解が1つとは限らない**ので、貼られた時点で一度解いてから載せる。

| 解いた結果 | ふるまい |
| --- | --- |
| 解が1つ | そのまま遊べる。ヒントとまちがい探しも効く |
| 解が複数 | 遊べる。「そのうちの1つを基準にします」と断る |
| 解が無い | 断って盤面は変えない |
| 重すぎる | 探索を打ち切って断る（`nodeLimit` 30万節） |

読み込んだ問題も途中経過は保存される（保存キーは盤面の本文そのもの）。
美術館ではない pid の URL や読めない本文は、盤面を変えずにその場で断る。

生成は問題を開くたびにブラウザの中で走る（1問あたり数ミリ秒）。
サーバも DB も無いので、過去のどの日付でも同じ問題がその場で再現される。

### 検証の内容 (`tools/verify.mjs`)

- **A. ソルバの基本動作** — 答えが手で確かめられる小さな盤面で、解の数まで含めて照合
- **A2. 総当たりとの突き合わせ** — ランダムな 4x4 盤面 60 個について、全白マスの部分集合を
  全部試す愚直な数え上げと `solve` の答えが一致するか。伝播と分岐が解を落としたり
  二重に数えたりしていないことの裏取り
- **B/C/D. 生成した盤面** — 各難易度 12 問について、盤面テキストから読み直して
  生成器とは独立に解き、①解が一意 ②解がルールを満たす ③生成時の解と一致
  ④数字が極小（どれか1つ外すと条件が崩れる）を検査
- **E. 日替わりの決定性** — 同じ日付なら同じ問題、違う日付なら違う問題、
  同じ日でも難易度が違えば違う問題
- **F. puzz.link との往復** — 手計算した符号との照合／白マスの連続が 20 で
  切れること／URL の受け取り方 5 通り／横縦の順番／ランダム 400 枚の往復／
  日替わりの問題を往復させても解が一意のまま／**上流(pzprjs)が自分で書いた問題
  `lightup/6/6/nekcakbl` との照合**（数字配置・本文の文字列・解の照明位置の3点）
- **G. 探索の打ち切り** — `nodeLimit` を渡すと打ち切って `aborted` で戻ること、
  渡さなければ今までどおりであること
- **H. オフラインの配線** — `sw.js` が保存するファイルの一覧と、実際に読み込む
  ファイル（`index.html` の `src`/`href`、`ui.js`・`pwa.js` の import、manifest の
  アイコン）が一致していること。絶対パスが混ざっていないこと（サブパスで壊れる）。
  manifest に 192/512/maskable が揃い `standalone` であること。**保存する一覧から
  1つ漏れると「オフラインで開いたら真っ白」になる**ので、機械で見張っている

### UI の検証の内容 (`tools/uitest.mjs` + `tools/selftest.html`)

追加の依存パッケージは入れていない。`tools/selftest.html` が本物の
`index.html` の中身を取り込んで `src/ui.js` を読み込み、実際の click /
contextmenu を投げて自己採点し、`tools/uitest.mjs` がヘッドレス Chrome
（`--dump-dom`）でそのページを開いて結果を読む。32 項目。

盤面が問題どおり描けるか / 右クリックの×印 / 照らし合いの赤表示 / 照明数の表示 /
途中経過の保存と復元 / やり直す / まちがい探し / ヒント2種 / 答えどおり置いたときの
クリア判定 / 日付の移動と URL / 手つかずの盤面を間違い扱いしないこと /
puzz.link の URL の書き出しと読み込み（貼った問題どおりの盤面になること・
読み込んだ問題でもクリアできること・別の種類の URL を断ること・今日へ戻れること）。

この32項目を **root 配信と `/daily-akari` 配信の2か所で回す**（合計 64 項目、
所要 2 秒ほど）。`rooiboshun.github.io/daily-akari/` のようにサイトの root
ではない場所へ置いても壊れないことを、静的な読み合わせではなく実測で押さえる
ため。`npm run uitest -- /好きな場所` でそこだけを検査することもできる。

Chrome の場所は環境変数 `CHROME` で指定できる。ブラウザが無い環境では
終了コード 2 で「見つからない」と言って止まる。

### オフラインの検証の内容 (`tools/offlinetest.mjs`)

`verify` の H 章が一覧の取りこぼしを静的に見るのに対して、こちらは実際に
**回線が無い状態を作って**確かめる。同じ Chrome プロファイルを使い回して3回開く。

1. 1回目 — サーバを立てて開く（Service Worker が入り、ファイルが保存される）
2. 2回目 — 保存済みの版で起動し、状態表示が「オフラインで遊べます」になる
3. 3回目 — **サーバを止めてから**開く。ここが本番

3回目で盤面のマス（81マス）・日付・難易度ボタンが揃っていれば、JS もソルバも
保存から読めていて、問題もその場で作れているということになる。8 項目。
root と `npm run offlinetest -- /daily-akari`（本番と同じサブパス）の両方で通る。

### 連続検査の内容 (`tools/soak.mjs`)

`verify` は各難易度 12 問しか見ないので、「ある日だけ問題が作れない」のような
日付ごとの当たり外れで起きる事故を取りこぼす。`soak` は指定期間の全日程・
全難易度を実際に生成し、1問ずつ ①例外を投げずに作れる ②盤面テキストから
読み直して独立に解くと解がちょうど1つ ③その解がルールを満たす
④生成器が返した解と一致する、を確かめる。併せて1問あたりの生成時間の
平均・中央・95%・最悪値を出す（ブラウザで開いた瞬間に作るので最悪値が重要）。

さらに **打ち切りまでの余裕** を報告する。①〜④の合否は事故が起きてから初めて
赤くなる遅行指標で、これだけを見ていると、採用率が下がる向きの変更（`blackRatio`
や `logicOnly` を触るなど）を入れても崖から落ちる直前まで緑のままになる。
実際に何回目の試行で当たったかを難易度ごとに集計し、採用率・中央・95%・最悪値と、
最悪値が `DEFAULT_ATTEMPTS` の何倍下にあるかを出す。最悪値が打ち切りの 25% を
超えると `<< 注意`、50% を超えると `<< 危険` を付けて、**失敗 0 件でも終了コード 1**
にする（崖の手前で止めるため）。

2026-09-14 から 730 日ぶん（2190 問）で失敗 0 件。当たるまでの回数は
easy 最悪 58 回（余裕 34.5 倍）/ normal 最悪 167 回（12.0 倍）/
hard 最悪 241 回（8.4 倍）。生成時間は easy 平均 1.9ms / normal 平均 9.9ms /

## 公開 (`docs/DEPLOY.md`)

**<https://rooiboshun.github.io/daily-akari/> で公開中**（2026-09-16〜）。

置き場所は2択だったが、このリポジトリをそのまま GitHub Pages にする案 A を
採った（master の root を配信）。更新は master へ push するだけで反映され、
ビルドも CI も挟まらない。公開直後に `/` と `src/` の4ファイルがすべて 200 で
返り、`.js` の MIME が `application/javascript`（ES モジュールが読める形）で
あることを実測した。

確かめてあること（相対パスのみ・localStorage の接頭辞・外部通信なし・
`.nojekyll` 不要）と手順は `docs/DEPLOY.md`。

公開に要るのは `index.html` と `src/` の5ファイル（`akari.js` `puzzlink.js`
`ui.js` `pwa.js` `style.css`）、オフライン用の `sw.js` `manifest.webmanifest`、
`icons/` の4枚。`puzzlink.js` は画面から見えにくいが `ui.js` が import している
ので、**1つでも欠けると盤面ごと描かれない**。

## オフライン対応 (`sw.js` / `manifest.webmanifest` / `src/pwa.js` / `icons/`)

**一度開けば、その後は通信なしで遊べる。** 問題は日付を種にして端末の中で
作られるので（サーバも DB も無い）、足りなかったのは「ファイルを手元に置いて
おく」ことだけだった。それを Service Worker が受け持つ。

| 機能 | 置き場所 | 説明 |
| --- | --- | --- |
| ファイルの保存 | `sw.js` の `ASSETS` | インストール時に全部取る。1つでも取れなければインストールごと失敗させる（中途半端に入って真っ白になるより、古い版が生き残るほうが良い） |
| 配り方 | `sw.js` の `fetch` | キャッシュ優先。返した後に裏で取り直して次回に備える（stale-while-revalidate）。同一オリジンの GET だけを扱い、外部（puzz.link）は素通し |
| 起動の保証 | `sw.js` の `navigate` 分岐 | ページそのものの要求には必ず手元の `index.html` を返す。オフラインでもホーム画面から起動できる |
| 更新 | `sw.js` + `src/pwa.js` | `skipWaiting` しない。新しい版があると画面の隅に「更新する」ボタンが出て、押したときだけ入れ替えて読み直す（遊んでいる最中に JS だけ新しくなる事故を避けるため） |
| 状態表示 | `src/pwa.js` → `#offline` | 「オフライン用に保存しています…」→「オフラインで遊べます」。**回線が無くなる前に保存の完了を確かめるため**のもので、飾りではない |
| ホーム画面 | `manifest.webmanifest` | `display: standalone` / 縦向き / 相対パスの `start_url`・`scope`（サブパス公開でも動く）。アイコンは 192・512・maskable 512 と iOS 用 180 |

`src/pwa.js` は `ui.js` から完全に切り離してあり、ここが丸ごと失敗してもパズルは
今までどおり遊べる。`file://` や `http://` では Service Worker が使えないので、
その場合は状態表示を出さずに黙って引き下がる。

キャッシュの名前は `akari-<VERSION>`。**公開するファイルを増減したら `sw.js` の
`ASSETS` と `VERSION` の両方を直す**（`npm run verify` の H 章が一覧の取りこぼしを
見張る）。
